# Story Agent V2：角色参考与画面一致性设计

日期：2026-10-23。状态：用户已认可方案、两次主要确认及 ArcReel 调研后的轻量取舍，并授权开始实施。按 M1 → M2 → M3 顺序交付。

## 1. 目标与已确认约束

用户希望通过角色图片、具体角色描述和分镜中的 `@角色名称`，控制跨镜头人物形象。角色基准图同时支持 AI 生成和用户上传。采用以下链路：

故事 → 角色与造型草案 → 角色定稿确认 → 带角色引用的分镜 → 分镜首帧 → 整组首帧确认 → 图生视频 → 一致性检查与局部修复 → FFmpeg 合成。

- AI 根据故事选择 1–20 个镜头，不规定固定镜头数；继续遵循用户期望的总时长和视频 API 支持的单镜头时长。
- DeepSeek 官方 API 负责文本规划及支持范围内的图片理解；OpenRouter 负责图像、视频生成。生成模型不本地部署。
- 保留 Pi Agent 的工具规划架构；项目数据库与任务执行器负责持久状态、校验、确认和付费操作边界。
- 两次主要人工确认分别是角色定稿、整组分镜首帧定稿。上传、编辑、预览不额外增加审批；产生费用的生成操作必须由用户明确发起。
- 按模块开发和测试，每个模块通过测试后进入下一模块，最后进行联调。大版本完成后询问是否推送 GitHub。

## 2. 选择的方案

采用“角色参考图约束分镜图片，再以分镜图片作为视频首帧”。`@` 负责绑定角色资产，实际视觉约束由生成请求中的参考图片承担。

仅将角色描述拼进提示词，工程简单，但缺少稳定的视觉锚点。直接采用多角色参考视频模型，链路较短，但受 API 暴露能力和参考数量限制。当前选择的两阶段方案能让用户在视频付费前检查角色、场景和构图，也便于局部修改。

该方案提升一致性控制能力，不保证生成模型完全复现参考人物，也不将固定 seed 当作身份一致性的保证。

## 3. 分阶段交付边界

| 模块 | 独立交付 | 测试通过的门槛 |
| --- | --- | --- |
| M1：角色库与引用 | 角色具体描述、青年／老年等造型、上传／生成基准图、版本定稿、分镜 `@` 绑定 | 数据约束、图片校验、引用解析、确认失效、生成任务恢复、界面与既有 V1 回归 |
| M2：分镜首帧与图生视频 | 角色参考进入图片 API、首帧编辑与整组确认、已确认首帧进入视频 API、按依赖复用产物 | 真实请求结构、能力不支持时阻断、首帧确认与视频版本绑定、去重恢复、素材传输、浏览器流程 |
| M3：检查与局部修复 | DeepSeek 图片检查、视频抽帧检查、结构化问题、定向修复与预算控制 | 检查结果校验、失败／不确定分支、修复上限、未受影响镜头复用、端到端联调 |

本文详细规定 M1，并固定后续模块必须兼容的接口与交互契约。M2、M3 各自在开始开发前补充实现计划及具体验收样例，不提前实施。

## 4. M1 角色资产模型

首版角色库归属于项目，不做跨项目共享市场。保留现有每项目最多 30 个角色的上限。

### 4.1 身份、造型、镜头表现分开

- **角色身份 Character**：不可变 `characterId`、可编辑显示名称、性格、关系和身份描述。项目内显示名称去除首尾空格后必须唯一。
- **造型 Look**：不可变 `lookId`，归属于角色，具有唯一的角色内造型名称，例如“青年”“老年”“冬装”。每个造型保存脸型、发型与发色、体型、年龄阶段、服装配色、标志性物件、禁止变化项等具体描述；未明确的特征允许留空，不凭空补成事实。
- **造型版本 LookVersion**：不可变版本 ID，固定该版本的描述、主参考图片资产、来源、生成参数、风格版本及内容摘要。修改描述或替换图片生成新版本，旧版本和历史产物保留。
- **镜头表现**：表情、姿态、动作、位置和临时道具归属于镜头，不覆盖角色身份与造型。

示例：“陈伯”是一个身份；“青年陈伯”和“老年陈伯”是两个造型，各有自己的主参考图。两者不依赖同一张图片强行表达年龄变化。

一个被镜头引用的造型，定稿前必须有一张可用主参考图和具体外观描述。M1 每个造型版本只选一张主参考图；更多角度、多表情图集留待后续需求，不作为首次交付前置条件。

### 4.2 图片来源与处理

- **上传**：独立二进制图片接口，单张最多 10 MiB，只接受 PNG、JPEG、WebP 静态图片。校验实际文件类型、解码结果与尺寸；最大 4096×4096 像素，不接受 SVG、动画或仅伪造 MIME 的文件。超限给出明确错误，不将图片放进现有 256 KiB JSON 接口。
- **AI 生成**：用户从造型描述主动发起一次图片生成，界面展示模型和费用估算；生成完成只是候选版本，不自动定稿。提示词由身份、造型、项目风格编译，要求单一人物、清晰面部、简单背景，减少无关元素。
- 上传后的文字说明可以手工填写。图片理解自动补全放在 M3，M1 不自动识别未接入的能力。
- 上传文件由服务端命名并写入受控数据目录，记录图片类型、尺寸、字节数及 SHA-256。客户端只获得资产 ID 和本机预览 URL，不能提供任意本地路径。
- 新增图片资产类别，明确区分角色参考图和现有镜头图。角色生成任务使用自己的造型版本标识，不能复用“没有 shotId 的 image job”作为全部角色的唯一任务键。
- AI 图片生成沿用 V1 的未知提交保护：可能已扣费但未完整落盘时，保留异常状态，禁止自动再次 POST。

### 4.3 角色定稿确认

角色定稿确认绑定项目风格版本、角色身份版本、所选造型版本和对应图片摘要的完整清单。确认后仍允许编辑，但内容变化必须撤销相关确认。纯显示名称更改不改变视觉版本，也不破坏既有引用。

无人物镜头允许没有角色引用；整部故事无人出镜时允许空角色清单，不能强行生成角色。

## 5. M1 的 `@` 引用与分镜编辑

- 分镜编辑器输入 `@` 时提供角色及造型候选项，如 `@陈伯·青年`、`@陈伯·老年`，选中后展示可点击的引用标签和主参考图。
- 引用的事实来源是结构化的 `characterId + lookId + lookVersionId`。文本中的名称用于阅读，不作为运行时身份解析依据。
- 使用单一默认造型时可以输入 `@陈伯`；存在多个造型且尚未选择默认项时必须让用户选择，不能静默猜测青年或老年。
- 用户直接粘贴的 `@名称` 必须经过候选匹配和绑定；无法匹配或有歧义时展示待修正项，阻止该版分镜定稿。文本里的普通邮箱不视为角色引用。
- 角色改名更新标签显示；删除已使用的角色／造型直接拒绝，并列出引用镜头。用户先替换或移除引用后才可删除。
- 保存分镜时同时校验引用属于本项目、造型属于角色、版本存在且与选定版本一致。模型产生的非法 ID 或 21 个镜头必须校验失败，不能截断或悄悄替换。
- AI 规划工具只能引用提供给它的资产 ID；新故事可以先生成角色／造型文字草案，用户补图并确认后，再细化镜头。模型只能提出草案，不能批准角色或调用付费生成操作。
- 现有 `shot.characterIds` 可作为兼容视图，但 V2 的明确造型引用才是视觉生成的依据，避免出现两套不同的真实来源。

## 6. M1 用户流程与代码边界

项目界面新增角色区域：角色卡、造型选择、具体描述、图片上传、生成候选图、版本记录和角色定稿。分镜卡新增角色引用编辑及图片预览，保留已有镜头描述、镜头时长等能力。

代码按现有项目组织扩展：角色领域校验、SQLite 资产与确认记录、角色服务、图片生成适配、HTTP 接口及 React 编辑组件。付费任务与持久化仍由宿主控制，Pi 的角色／分镜工具只提交经过校验的数据。

M1 交付后可以创建并确认角色、保存稳定引用，但不声称现有视频已受角色图片控制。V2 视频生成按钮在 M2 接入前显示功能尚未开放；现有 V1 项目的原流程仍可使用，界面标明其没有角色参考约束。

## 7. 后续模块的固定契约

### 7.1 M2：首帧生成和第二次确认

- 编译每个镜头的输入：项目风格、明确的角色造型版本、按顺序排列的参考图片、场景构图和动作。提示词明确参考图片与角色的对应关系。
- 调用前检查实际可用端点是否接受 `input_references`，以及参考数量、分辨率、画幅是否受支持。超出能力时在付费前报错，不能退回纯文本生成并宣称已使用参考图。
- 每镜头保存独立的首帧图片版本；用户可局部修改和重新生成。全部当前首帧及分镜内容在同一预览清单中确认，之后才能开始图生视频。
- 第二次确认绑定全部当前首帧资产摘要、角色造型版本、风格、镜头文本、时长及生成模型配置。确认同时发起用户选择的批量视频任务；生成期间暂不允许编辑输入，防止并发产生旧版本结果。
- 视频请求使用已确认的镜头首帧 `frame_images`，不能直接把孤立人物肖像当作已经构图的首帧，也不能只把本机预览 URL 发给云端。
- 素材传输层必须验证当前提供方支持的图片传输方式。优先使用明确支持的 Base64 data URL；若视频端点只接受可公网访问的 HTTPS 资源且没有已配置的上传通道，则在提交前阻断并提示缺少素材传输配置。不能自动公开上传用户角色图片，也不能假设图片 API 的 Base64 支持适用于视频 API。
- 用规范化的实际输入、模型参数和依赖图片摘要计算任务指纹；修改一个角色只使依赖它的首帧与后续视频失效，其他有效产物可显式复用。参考顺序也计入指纹。
- 保留唯一执行约束、云任务 ID 持久化、未知提交阻断和已完成产物校验。复用不能凭文件名判断，也不能将部分失败当作完成。

### 7.2 M3：检查、修复与费用

- DeepSeek 通过官方 API 对角色参考和镜头图片进行图片理解；视频使用 FFmpeg 抽取首、中、尾帧后检查，不假设模型支持整段视频输入。
- 检查返回 `pass / fail / uncertain`、问题类别、角色／镜头 ID 和对应帧的证据说明。关注身份／年龄造型、服装、人数、关键道具、构图与剧情要求；跨镜头加入时代、手持物和位置的连续性信息。
- 检查工具失败或证据不足归为 `uncertain`，不能当作通过。机器检查不能替代真实人工质量标注。
- 检查可以自动运行；首次交付中，付费修复由用户选中失败镜头、查看费用后明确发起，每次操作每个镜头最多提交一次。不会因检查失败自动不断生成。
- 首帧修复会撤销该镜头下游视频的有效性；修改后的首帧重新进入第二确认清单。仅重做视频时保持已确认首帧及其版本，保留旧片段供比较。
- 输出保留模型、参考资产、提示词、确认清单、检查结论、修复及费用估算记录。展示“未检查”“有疑问”“用户接受”等真实状态，不能将手动接受伪装成模型通过。

## 8. 版本、存储与 V1 兼容

SQLite 采用可重复检测的增量迁移，保留既有项目、事件、任务和产物；迁移前创建被 Git 忽略的本地备份。旧项目继续读取、播放和沿原 V1 流程执行。

新建项目采用 V2 流程。旧项目进入 V2 必须通过明确的“启用角色参考”操作：转换文字角色为草案，撤销当前执行许可，重新完成角色和首帧确认。不会在迁移或服务启动时自动发起付费请求；旧视频留在历史记录。

新增角色版本、资产、审批清单和依赖指纹，不改变历史文件内容。持久任务恢复只能恢复原确认输入；无法确认是否已提交云端的任务继续保持 unknown，不根据新版本重发。

## 9. M1 测试与验收

按子模块先写能验证行为的失败测试，再实现，随后执行累计回归；不先并行开发三个大模块。

1. **领域与存储**：身份／造型／版本归属、重名、不可变版本、项目隔离、重启读取、旧库迁移、确认清单失效、无人故事。
2. **图片输入与任务**：三种格式、伪造类型、损坏图片、超限尺寸和字节数、非法路径；AI 返回失败、超时及可能扣费后的落盘失败；未知任务不得重提。
3. **引用与规划**：多个年龄造型、角色改名、非法／歧义引用、被引用资产删除、模型伪造 ID、镜头数量 1／20／21；结构化引用与界面显示保持一致。
4. **接口与界面**：真实上传与预览、上传／生成两种来源、角色定稿、选中 `@` 候选、编辑后确认失效、付费入口状态、刷新恢复。错误不能暴露密钥或本地路径。
5. **累计回归**：类型检查、既有 Vitest 与浏览器测试、生产构建；M1 浏览器用例包含真实图片文件与 SQLite，但云端使用明确标注的测试替身。

使用“老爷爷看到年轻时写给妻子的信，回忆重逢”作为固定验收故事：同一身份的青年／老年造型分别引用；至少包含一组双人镜头和一个无人道具特写。不把镜头数写死。

真实付费冒烟与离线测试分开记账和记录；没有真实调用的部分不能标记为真实云端验收通过。M1 完成后只汇报角色与引用能力，画面一致性效果留到 M2／M3 实测。

## 10. 最终联调与效果证据

完整联调覆盖上传／生成角色 → 两次确认 → 带首帧的视频生成 → 抽帧检查 → 单镜头修复 → 合成播放，以及中途重启、未知提交、用户改版和过期确认请求。

固定评测故事与人工标注，比较纯文生视频、仅角色文字、参考图加首帧、加入检查修复四种设置；记录角色与造型正确率、跨镜头一致性、剧情符合程度、重生成次数、时延与实际费用。相同故事和参数版本留档，小规模结果如实说明样本范围，不预设提升百分比。

V2 首次交付不包含本地模型、LoRA／训练、跨项目资产市场、自动配音口型、完整场景与道具资产编辑器。全局风格及镜头内道具／位置说明属于本次描述字段，不扩展成另一套素材平台。

## 10.1 ArcReel 调研后的范围细化

- M1 为角色增加别名（同一项目内名称／别名不能归属于不同身份）；界面展示引用造型与参考图，编辑前可查看受影响镜头。首版拒绝删除已引用角色，不实现复杂资产合并。
- M2 增加独立首帧的审核联系表、可选单镜头视频试跑、当前／过期／缺失／阻塞状态。联系表只用于并排审阅，不以联合出图后裁切替代独立首帧。
- M3 检查除外观外还覆盖剧情目的、现在／回忆阶段、关键道具与镜头衔接。通过固定故事评测定位准确性、局部修复成本和对未修改镜头的影响。
- 不扩展为多集平台、供应商市场、ComfyUI 工作流、完整剪辑器或多 Agent 层层编排。
- 参考：[ArcReel 工作流](https://docs.arc-reel.com/guide/workflows/)、[供应商配置](https://docs.arc-reel.com/guide/providers/)、[素材审阅架构](https://docs.arc-reel.com/dev/architecture/)。借鉴公开机制，独立实现。

## 11. 调研依据与能力边界

以下为 2026-10-23 调研依据，实施时再次检查端点能力，不把目录元数据当作质量评测结果：

- [Runway：通过引用媒体控制生成](https://help.runwayml.com/hc/en-us/articles/52963720640275-Using-reference-media-to-guide-your-generations)：命名参考和 `@` 引用的产品先例。
- [Runway：长视频与电影制作](https://help.runwayml.com/hc/en-us/articles/26871350018835-How-to-create-longer-videos-and-films)：人物与场景参考、分镜预规划。
- [OpenRouter 图片生成](https://openrouter.ai/blog/tutorials/image-generation/)：图片参考输入及端点参数检查。
- [OpenRouter 视频生成](https://openrouter.ai/docs/guides/overview/multimodal/video-generation)：首尾帧输入、异步任务及不同模型的能力差异。
- [OpenRouter Hailuo 3 Max](https://openrouter.ai/minimax/hailuo-3-max)：当前默认视频模型的首尾帧能力；没有据此认定开放了多人物参考视频接口。
- [Veo 视频生成](https://ai.google.dev/gemini-api/docs/veo)：多参考与视频一致性的另一实现路线；不代表 OpenRouter 同样开放全部参数。

本次公共目录查询中，FLUX 3 Image Klein 列出最多 10 个参考输入，Hailuo 3 Max 列出首／尾帧支持。这仅用于选择首帧驱动方案；模型名称、参数与价格继续通过能力检查及实际账单确认。
